## D14. Step 7 implemented with a simulated witness

Implemented:

- `weaver_contracts.checkpoint`: the `wx-checkpoint-1` statement, its exact signing bytes
  (domain prefix `wx-checkpoint-1\0` plus WX-CJSON-1), and strict parsing.
- `weaver_verifier.checkpoint.custody_report`: pinned-key signature checks, split-view and
  witness-equivocation checks, and the prefix check against the snapshot.
- `weaver_witness`, a reference witness: append-only, fork-refusing, with every signature and
  every refusal in its own log, which it re-verifies against its own key on start.
- A new trust domain, `witness`, which may import `contracts` and `verifier` and never
  `runtime`. UADR-0001 is amended to add it.
- `tests/custody`: acceptance tests A1–A8 and 15 edge cases. Six mutations in
  `tools/check_verifier_mutations.py`, all detected: five by a wrong verdict, one (pinned key)
  by a crash.

Two decisions taken while implementing, which depart from the DRAFT design:

1. **There is no `WITNESSED` status.** A consistent result is `CHECKPOINT_CONSISTENT`, with
   the number of distinct pinned witnesses (`UNCORROBORATED` for one, `CORROBORATED` for two or
   more) and `independence: NOT_ESTABLISHED` on every report. Code can check signatures and
   consistency; it cannot check who holds the keys, and a status named WITNESSED would read as
   that claim. A1's required result becomes `CHECKPOINT_CONSISTENT`.
2. **Staleness is counted in entries, not intervals (A8).** Checkpoints bind content, and the
   verifier has no trusted clock. The report gives the number of entries after the newest
   checkpoint and says `COVERED_TO_HEAD` only when there are none.

What this does not establish: every witness in the tests is simulated by keys the test
harness generates, in the same process that writes the ledger. So the evidence is R2[self]
and the witness level stays W0. Fetching checkpoints from channels the operator does not
control, and the key-rotation procedure, are not implemented.

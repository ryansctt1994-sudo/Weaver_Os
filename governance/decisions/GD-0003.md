## D8. C-GATE-001: direction chosen, not closed

The decided direction is a **same-transaction design for software-governed commits**: the
commit transaction must evaluate the authoritative veto and revocation state under the same
serialization boundary that decides whether the commit is accepted. Recording a veto in the
ledger is necessary but not sufficient.

**Open design question.** The current veto source is the in-process software twin
(`TwinVeto` over `LuciferLatchTwin`), so a SQLite transaction cannot read it. Any design has
to choose one of these:

- the veto and revocation state lives in the same database and is read inside the commit
  transaction; or
- it is captured under a single serialization point the commit also passes through.

Neither is implemented.

**Closure criteria.** C-GATE-001 may be closed only when a test that fails on the current code
passes on the new design. That test must show that a conflicting veto or revocation landing in
the pre-commit window cannot be missed under the defined commit semantics. Adding another
check does not close it, because the window only shrinks.

**Limits that remain regardless.**

- The hardware veto is a separate, fail-closed physical mechanism. It is not closed by the
  software design.
- RTL and Python-twin equivalence is evidence about modeled behavior only. It is not evidence
  of physical confinement.
- Until closure criteria are met, the software gate is **advisory** with respect to the
  final-gap race. Effect confinement is not claimed.

No execution authority is promoted on the strength of either claim alone.

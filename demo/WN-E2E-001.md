## Exact scope

This composes the existing `EpistemicKernelValidator`, ordinary/authority-leak
JSON fixtures, and `TriadLedger`. It adds a small state adapter, persisted receipt
binding, semantic replay, fresh-process reproduction, and tamper probes. It does
not replace the runtime, Receipt Core, or the existing four-case demo.

Protected state is exactly `(authority, artifact, revision)`. An accepted ordinary
fixture updates artifact/revision; a rejected proposal changes none of these.
The audit log still appends a rejection event. “Zero mutation” refers to protected
state, not to the audit log or the entire filesystem.

1. Existing ordinary fixture: ACCEPT and a non-vacuous protected-state change.
2. Existing self-authority fixture: REJECT; identical before/after state hashes.
3. Fresh process: reload and validate the ledger, recompute verdicts and receipts,
   and compare final state. Another process regenerates byte-identical receipts,
   ledger, state, and manifest from fixtures.
4. Change ACCEPT to REJECT in the persisted receipt: verifier exits 1.
5. Change ACCEPT to REJECT in the persisted chronicle: verifier exits 1.

The manifest pins the source bytes and output bytes; runtime version is in the
run summary. Fixed event timestamps are fixture data, not execution timestamps.
The CI addition runs on the repository's existing Python 3.10/3.11/3.12 matrix
and retains outputs. A local run is not evidence that hosted CI has passed.

## Adversarial coverage

Eight new pytest cases cover the full demo, stale ledger payload with recomputed
outer file hash, deliberate hash-gate removal, mutation of protected state on
rejection, empty history, truncation, reordering, and a rewritten receipt with a
recomputed outer file hash. The stale-payload negative test was also run against
a temporary source mutant removing `verify_event_hash`; that test failed as
expected. The original source was restored afterward.

## Limits and next integration gate

The existing validator checks only the presence of synthetic evidence-reference
lists. It does not authenticate a steward or prove a real grant. ACCEPT therefore
means accepted under this fixture policy, not genuine operational authorization.
The adapter allows only ORDINARY transitions; it cannot certify CVP promotion.
It hashes the proposal (including the legacy target-state field), but computes
the resulting state itself rather than trusting that field as a state commitment.

Unsigned local manifests and unsigned ledger entries establish internal byte
consistency, not authentic history. An attacker able to rewrite every artifact
and checkpoint coherently can evade these local comparisons. There is no external
freshness anchor, concurrency/crash proof, distributed witness, live lease, key
management, or real-world effect boundary. No claim of E4, formal/runtime
correspondence, or ASI/RSI capability follows.

Next: review this adapter, pin the reviewed commit/environment, replace synthetic
authorization with the canonical live-grant path, and obtain an independently
executed receipt for the exact narrow claim. Keep genuine authorization and
independent reproduction open until those separate gates are met.
